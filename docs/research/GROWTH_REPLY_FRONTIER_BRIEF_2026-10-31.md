# Growth OS: problem statement and evidence for independent assessment

Date: 31 October 2026. Repository: `/home/ubuntu/repo/x_test`.
Account: `@ham_zax`. Latest experiment commit: `651cb33`.
Purpose: give an independent frontier model enough context to assess the problem.
This report selects no solution and authorizes no new experiment or deployment.

## 1. The goal

Hamza wants an agent to operate his technical developer/builder X account around
the clock. The agent must discover opportunities, understand posts and conversations,
choose whether to participate, write appropriate content, and act through Growth OS.
Replies are the current quality bottleneck. Posts, Quotes, Reposts and relationships
also belong to the intended product, but this investigation does not evaluate them all.

The intended deployment model is DeepSeek V4.1 through OpenCode, usually at its
highest exposed reasoning setting. The motivation is sustained affordability and
continued availability. A Codex subscription may end. A solution that permanently
requires Terra for every reply does not satisfy the preferred deployment goal.
No measured monthly cost or token budget has been established.

The target is a model that is good enough in the actual agent system, not one that
can occasionally write a good reply in an isolated chat. Growth OS must preserve
that capability when it adds persona, behavior selection, source context, tools,
instructions, memory, validation and publishing workflow.

## 2. The owner's complaint

The agent writes on Hamza's behalf but often sounds like an unsolicited adviser,
senior reviewer or product evaluator. A reply can mention the right topic while
making the wrong contribution to the conversation. Some replies also misunderstand
or overlook information already present in the source.

The desired voice is a participant and peer. Interest, curiosity, humor, support,
agreement, disagreement, useful technical explanation, invited advice and silence
are all valid. Every action needs a purpose. Every action does not need new
technical information. The owner rejects excessive rules that make writing stiff
or turn ordinary reactions into a verification exercise.

The problem is not equivalent to excessive length or formal vocabulary. A short
reply can still talk down to someone. A detailed answer can be appropriate.
Lowercase text, slang, intentional errors, obligatory jokes or a fixed word count
are not accepted definitions of human writing.

## 3. Product and session context

Growth OS persists persona, candidates, queue, relationships, approvals and
measurements. ARM is the production operator. WSL is test-only. Public sends use
the Growth OS claim and publication workflow. The browser is a transport, not an
independent source of publication authority.

The session began with a broader issue inventory and operational repairs. Recorded
work covers response observation, follower consistency, outcome metadata, upstream
code trust, source freshness, readiness displays, topic research/citations,
analytics collection outcomes and attached-browser lifecycle. These changes do
not establish reply quality. Earlier implementation summaries and TASKS.md contain
their individual acceptance limits. This report does not declare all original
issues closed or the account ready for unattended operation.

Authentication and browser access were investigated earlier. The owner authorized
persistent credential storage. This report includes no credentials. Later voice
experiments use public captured sources and disposable state, not live sends.

The owner then made message quality the main concern. He asked us to inspect actual
October replies with their parent posts, rather than infer the problem from a few
short examples or ask him to articulate a complete style specification first.

## 4. Evidence from published replies

The audit captures 458 unique replies dated 3–24 October 2026. It obtains 456
immediate parent texts. Of the replies, 448 match confirmed Growth OS publication
records. Ten have no matched record. Their human or agent origin is not established.
The selected replay set contains 22 assessed exchanges.

Observed failure classes include:

- Responding to a launch by announcing the test that would make it worthwhile.
- Implying an unshown defect or assigning the author an unasked task or metric.
- Asking a question that the source already answers.
- Replacing a reaction with a general technical lesson.
- Turning an available feature into a universal claim or decisive causal boundary.
- Selecting one social purpose while realizing a different, evaluative role.

Some replies are useful controls. Advice is appropriate where someone asks for it.
We have no defensible percentage of bad replies and no causal follower-growth claim.
Stored queue metadata is not an immutable trace of every historical generation.
Current code cannot prove exactly what each past model saw.

The audit also identifies current technical contributors: extended note text is
omitted at the installed parser boundary, contribution fallbacks favor technical
or learning choices, and missing Writer archetypes can default to synthesis.
These are separate code facts and plausible contributors. They are not one proven
explanation for the entire historical corpus. The parser pin postdates those replies.

## 5. Authoring and review paths

The structured Writer builds a packet from source, persona, selected behavior and
other context. The Writer realizes the selected behavior. Independent content
review and deterministic binding inspect structured output and evidence.

The attached reasoning operator also writes direct replies and submits them through
`act`. Changing the Writer prompt alone does not cover that route. The live direct
`act` path does not invoke the Writer content review used in our offline diagnostic.

Persona is a separate owner. Purpose, mode, affect and depth are separate behavior
fields. These inputs can influence writing before an extra voice instruction is
appended. The model provider also contributes its own harness. Our experiments
are not raw inference with an empty system prompt.

## 6. Initial prompt and persona experiments

A four-source DeepSeek pilot compares current static guidance with two changes:
one replaces reply instructions, and the other removes three systems-focused
persona cues. Both retain unwanted evaluator framing in some outputs. Some outputs
improve, and useful direct answers survive. Neither candidate earns production use.

The pilot is a static simulation, not the production Writer or attached Growth Run.
It uses one sample per source per condition. It does not establish a failure rate,
isolate a single causal sentence, or prove that the model cannot improve.

## 7. Terra and other model comparisons

Terra medium receives the exact original baseline task on the same four cases.
No special persona or revised reply prompt is added for Terra. The parent finds
Terra closer to the desired direction: it skips one weak opportunity, gives a
relevant celebration, reacts less dismissively to the phone agent, and directly
answers an invited human-approval question. That is a small qualitative result.
Provider and reasoning setting change along with the model.

MiMo V2.6 Flash Free, GLM 5.3 Flash Free and Big Pickle receive the same baseline
task through the available Pi catalog. The requested settings are the highest
exposed settings: MiMo high, GLM max and Big Pickle high. Big Pickle's underlying
model identity is unknown. Their samples also show general lessons, evaluator
framing, unsupported broad claims or feature combinations. Some individual outputs
fit. Higher requested reasoning does not by itself remove the pattern.

Sol acts as the parent analyst/designer and later writes ten illustrative replies
in chat. Those examples demonstrate a proposed direction, not a controlled Sol
solver result. We did not establish that Sol reliably solves the deployed problem.
We also did not establish that DeepSeek or all smaller models are incapable.

## 8. The two-model idea

The owner proposes a cheap model for most agent work: discovery, source reading,
opportunity selection, tool use and orchestration. A stronger model would be
called less often to decide whether an opportunity deserves a response and then
write a good reply or post. Terra was the proposed stronger model.

Discussion also considers a stronger model guiding or reviewing a cheaper model.
These are different divisions of work. They leave open who chooses the intent,
who writes the final text, who checks factual support, and how disagreement is
handled. No complete production routing, call-frequency policy or measured cost
comparison was implemented or accepted.

The owner later asks us to hold the live Terra dependency because OpenCode will
remain available longer. He subsequently authorizes Terra high for experiments.
That later permission does not make a two-model production design the selected
solution. The deployment preference remains DeepSeek good enough on its own.

## 9. Fresh DeepSeek experiment without the old packet

The owner asks for a short new prompt without accumulated persona and instruction
baggage. Six DeepSeek max calls test four prompt versions, an exact repeat and a
four-source transfer batch. The short packet omits old persona, operating-standard
text, purpose labels, past replies and previous output. The provider harness remains.

V4 produces more interested, conversational reactions in the parent's assessment.
This is evidence that DeepSeek can change register. The exact repeat still changes
a source quantifier into an every-tool-call claim. The transfer output adds an
unrequested field. Better social register does not establish factual reliability
or structured-runtime compatibility.

Several dimensions differ from the first pilot: context size, task role, purpose
field and prompt examples. Their individual effects were not isolated. One example
also resembles a transfer topic, which weakens that case as a novelty check.

## 10. What we actually used Harness² for

The owner introduces Google's Harness² repository and the propose/probe/compose
idea. We use the installed native library for a bounded offline Growth OS adapter.
This is not the browser tool WebHarness. We do not treat claims in the supplied
video transcript as independently verified research findings.

The adapter runs actual `core.recursion.run_mode`, sequential k=1. It captures a
baseline, asks an editor for two extra-instruction variants, runs the probes and
asks for composition. The editable surface is an extra voice fragment, rather
than production code, facts, schemas or persona. Native accounting records four
rollout labels and three editing/composition stages.

DeepSeek max is the solver. Terra high supplies editing and independent content
review in this experiment. T3 dispatches exact target requests. The Python adapter
exchanges serialized requests and completed receipts. It does not secretly launch
a replacement model CLI. The experiment is task-level recursion, not cross-task
library learning, reflection or automatic deployment of a winning harness.

The composer returns KEEP_BASE. Both probe candidates retain unsupported grading
or causal comparisons. The composed baseline reuses an identical cached execution.
It is not another independent generation. No improved style earns acceptance.

## 11. Transfer into the real Growth OS context

The integrated benchmark captures actual Writer packets, schemas and review prompts
through injected callbacks. It also replays the attached reply instructions as a
separate direct lane. The direct lane omits browser, room and full operator history.
It adds content review diagnostically, not as proof of an existing live `act` gate.

Eight unique generated outputs cover the current Writer, V4, native probes, a
matched Terra-high Writer call, a celebration control and two direct-instruction
conditions. All satisfy their output schemas. All original content reviews fail.
Neither statement establishes that every reply is equally bad or every review is
correct. Only two sources are used in this integrated wave.

DeepSeek's full-context V4 reply includes:

> the recovery part is the real product. editing files from a phone is the easy claim; surviving android killing the foreground service mid-edit is the hard one.

The source says recovery features help continuation. It does not establish that
specific failure or the decisive comparison. The shorter prompt's earlier success
does not reliably transfer into this Writer context.

The matched Terra-high output is more restrained:

> The sweet spot for a phone coding agent is a contained fix: review the diff and push without getting back to a PC.

The reviewer still blocks it for source attribution. One sample does not establish
consistent Terra superiority, a successful model switch or owner acceptance.

## 12. Review calibration is a separate problem

One review flags “congrats on 1.6” as an unsupported factual claim. That is a
questionable classification of a social act. The same reply says “an agent-built
canvas,” while the source says an agent can create a canvas. That separate objection
has substance. The whole reply is not a clean positive control.

An optional offline calibration fragment asks the reviewer to distinguish social
acts, immediate affect and preference from concrete claims. It requires no technical
contribution, caveat, question or factual citation for an ordinary reaction. It
retains concrete objections to invented product behavior and personal history.

Two review-only calls reuse saved outputs. The calibrated celebration review stops
listing the congratulation as a claim. It still flags the canvas wording. The
calibrated Android review retains the unsupported causal comparisons. Both whole
replies remain blocked. This narrows one classification error. It is not proof of
calibration across topics or a reason to optimize toward universal approval.

There is an unresolved contract interaction: the content standard lets a Reply
rely on visible source context, while source-claim binding requires explicit
attribution words. Some failures reflect this declared rule, not hallucination.
No production verification or attribution rule changes during this investigation.

## 13. Isolated selected-behavior comparison

After the integrated wave, two new DeepSeek max calls hold source, persona, Writer
contract, model and settings fixed. Frozen packets differ only in selected behavior.
The treatment changes purpose, mode, depth and reason together from judgment to
social participation. It is one behavior intervention, not one changed scalar.

Judgment output:

> the phone part is the demo. the tool cards are the product — every call gets a diff sheet and its recorded check outcome instead of a hidden edit. strip that out and it's just another chat window in your pocket.

Social output:

> fixing a bug from the phone, then confirming the commit landed on the remote — that's the pitch and it's a good one. the resume cards are the unglamorous bit that decides whether it holds up.

The social opening changes, but the decisive product test remains. The judgment
sample also overstates per-call diff support. Changing selected behavior alone
does not remove the problem in this pair. One sample per condition does not prove
that behavior has no effect or identify the remaining cause.

## 14. Benchmark capability and engineering status

The reusable offline benchmark can capture exact requests, select available
writer/reviewer/editor models and options, change an extra writing fragment,
compare reviews without regenerating text, and retain raw output after failures.
It uses disposable application state and never invokes publication claims or sends.
Reviews are diagnostic. No numeric voice score or pass quota chooses a winner.

Engineering corrections cover timestamp-driven request drift, stale frozen
behavior, cached inspections surviving owner-code changes, extra execution
settings and empty error diagnostics. One independent packet review identifies
comparison defects, and the parent repairs them in one round.

Final recorded checks: 406 Node tests and seven Python tests pass. These tests
cover software behavior, not writing quality or unattended agent readiness.
The integrated graph uses 27 of 28 dispatches, including engineering, diagnosis
and review attempts. The later behavior comparison uses its own two-call budget.
Actual token usage, provider compute allocation and monetary costs remain unknown.

The archive retains exact inputs, outputs, receipts, native cycle and test logs.
Model jobs are text-only by instruction. That is not an OS-level sandbox claim.
Native imports initialize their normal dotenv configuration. Environment values
are not serialized into the model payload. No credentials belong in these reports.

## 15. What the evidence establishes and leaves open

Established: the published corpus contains conversational-role failures. Several
offline samples reproduce them. DeepSeek is steerable under shorter context.
That improvement does not reliably persist under the tested Growth OS context.
Factual overreach and review overclassification coexist. Changing selected
behavior alone does not eliminate grading in the latest pair.

Not established: one root cause, an irreducible DeepSeek capability limit, a stable
model ranking, reliably correct Terra or Sol output, a production voice repair,
a beneficial follower effect, or safe 24x7 operation after these experiments.

Plausible contributors include context interactions, persona framing, selection
defaults, model/provider priors, source fidelity and review contracts. Their
individual causal weights remain unknown. Repeating a previously unsuccessful
prompt or persona change without a new distinction would add little evidence.

## 16. Request to an independent frontier model

Assess the problem from the goal and evidence above. Do not assume the solution
must be a longer prompt, a stronger model, a second reviewer or fewer safeguards.
Do not accept the parent's preferred explanation as established causality.

Address these questions:

1. What is the narrowest defensible problem statement? Which failures are distinct?
2. What evidence supports a capability limit versus an interaction in the harness?
3. Which existing observations contradict each plausible explanation?
4. What is the cheapest next experiment that would distinguish the leading causes?
5. What would count as sufficiently good before testing an unattended live agent?
6. How can evaluation respect creative, contextual writing without accepting
   invented facts or turning every social act into an audit?
7. If a single cheap model is viable, what evidence would demonstrate that?
8. If two models are justified, where must responsibility lie, how often must the
   stronger model run, and what result would justify the continuing dependency?
9. Which current prompt, persona or review components would you retain, test,
   simplify or remove, and why? Separate hypotheses from implementation proposals.

Return an evidence-based assessment, missing information that materially changes
the decision, and a minimal discriminating plan. Do not implement anything or
declare a model incapable from these small samples. The owner decides direction
after seeing that assessment. The desired outcome is affordable, context-appropriate
24x7 operation, not winning a benchmark or making every reply pass a reviewer.
