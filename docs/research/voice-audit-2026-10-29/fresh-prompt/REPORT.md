# Fresh DeepSeek prompt experiment, 29 October 2026

## Outcome

DeepSeek can change its writing register with a small, fresh instruction. The
earlier large-packet trials did not establish a fixed model inability. Four prompt
versions, an exact repeat, and a new-source check now provide a more useful result.

Version 4 is the provisional candidate. It improves the conversational role in
the parent's assessment. The repeat exposes factual drift, so this is not a final
equilibrium or production acceptance. The transfer response also adds an unwanted
field. Both defects remain in the saved evidence.

All six calls use OpenCode `opencode2api/deepseek-v4.1-flash-free`, variant max.
Terra stays on hold. No production persona, prompt, model, policy, or service changes.

## Fresh conditions

The user explicitly requests a new short prompt without the old baggage. The
solver receives source posts, a short style instruction, and a small output
contract. It receives no old persona, long operating standard, old replies,
purpose labels, prior trial output, or analyst assessment.

The task role changes from research to general. The response drops the purpose
field, which previously encouraged a categorical label before text. These changes
occur together with context reduction. The experiment does not isolate which
change explains the difference. It establishes practical steerability under the
new condition, not a proven single historical cause.

The provider's own harness remains. This is not a raw model with an empty system
prompt. Every call starts a new child context and uses no tools or live X access.
The parent uses the X-content skill to assess fit. That skill text does not enter
the solver packet. No private workspace memory enters the experiment.

Calibration sources are VA-03, VA-14, VA-16, and VA-21. Before generation, the parent
freezes transfer sources VA-04, VA-06, VA-10, and VA-22. The four leave the previous
unused set in this new experiment. Fourteen earlier cases remain unused.
The parent already knows the historical report, so this is not blind evaluation.

## What changed in the prompt

V1 asks for an ordinary peer reply. The result invents "I keep going back and
forth" about a design choice. The source supplies no such personal history.

V2 emphasizes the present reaction and optional questions. It stops the invented
past but brings back a general lesson about what agent demos usually neglect.
Replacing questions with opinions is not sufficient by itself.

V3 demonstrates short conversation turns with three newly written, explicitly
invented examples. They describe a launch, a repurposed photo frame, and an agent
permission question. They are not owner biography, published replies, or accepted
voice examples. The parent does not copy earlier Terra output into the prompt.

V4 retains those examples and adds a narrow boundary: stay with this post, omit
unsupported generalizations about other people or products, and join the author
rather than decide whether their work earns approval. This targets actual failures
from the previous probes. It does not ban technical opinions or advice.

The synthetic photo-frame example overlaps thematically with transfer case VA-06.
It does not supply the real source or its answer. That case is near transfer,
not a strong independent novelty check. The other transfer cases address a
workflow question, multimodal search, and invited architecture advice.

The complete candidate is in `prompt-v4.txt`. Its examples and added instruction
remain part of the tested prompt. The short opening alone is not the tested result.

## Concrete improvements

The initial V4 Android reply is:

> The recorded check outcomes are the detail I like most. Working from a phone is one thing, seeing what the agent actually ran is another.

It responds to an actual feature as a personal reaction. It does not assign a
reliability test or declare other products to be demos. The launch reply expresses
interest in the agent-created canvas and congratulates the author. The approval
reply chooses merging a pull request and explains the desired review.

On the new search source, DeepSeek notices the supplied podcast example instead
of requesting an already-advertised benefit. On the code-review architecture
source, it proposes dropping queued work when the PR closes. The author explicitly
asks what to add, so an engineering recommendation fits that conversation.

The workflow source asks whether the speaker keeps the prompt in a file. The
packet lacks verified owner practice. DeepSeek offers a file-based recommendation
instead of inventing that history. That is honest, though an answer about actual
practice would require real owner evidence. The photo-frame reply expresses an
opinion grounded in the listed root/browser capability and price.

## Remaining defects

The exact repeat changes available diff sheets into "diff sheets on every tool
call." The source says every tool call has a card. It does not promise a diff
sheet for every call. Improved voice does not fix factual precision.

The repeat also says the speaker cannot un-merge something others already pulled.
That argument is too broad without distinguishing reverting changes from undoing
their distribution. The policy preference can be valid while its explanation
overreaches. A statement about deployments making the speaker nervous remains a
proposed voice choice, not a confirmed owner belief.

The transfer output adds an empty `text_alt` field to each reply. The instruction
requested caseId, decision, and text. The raw output is preserved with this
deviation. Passing JSON parsing does not mean passing the requested field contract.
No production parser or review consumes these drafts.

Some reactions remain polished or evaluative. The owner has not accepted them as
his voice. There is no quality percentage, causal claim about growth, statistical
stability estimate, or evidence that every future post will work.

## What the evidence supports

The model is steerable. A promising DeepSeek-only direction exists. Extra model
spend is not a demonstrated prerequisite for improving this failure class.

The explicit calibration task shrinks from the earlier 41,595 UTF-16 characters
to 4,006 for selected V4. This measures supplied task text, not the whole provider
context, token cost, or latency. Usage receipts are unavailable.

The evidence does not justify restoring all old persona material around the new
prompt and assuming the effect survives. It also does not identify which old
instruction was causal. Reintroducing useful account facts requires an actual
integration check. Long documents and behavior labels can change the result again.

## Next boundary

Keep V4 as a provisional writing contract. The next experiment needs exact factual
support and the real structured-output boundary, while preserving this register.
The existing AI runtime already validates schemas. Test that owner before adding
another prompt rule for every formatting error. The existing independent review
must face the actual drafts before a production claim.

The direct `act` route and routed Writer still need separate integration evidence.
This experiment changes neither path. Do not silently restore a Terra dependency,
invent owner experiences, rewrite persona facts, or enable continuous operation.

All six dispatches are consumed. XR-14 stays in-progress. Source data, prompt
versions, complete requests, hashes, output, and task identities form this restart
checkpoint. Automated visual checking remains blocked by the host sandbox policy.

## Short retrospective

A fresh peer prompt changes the behavior more than the earlier constrained
projection tests suggested. Future model-capability claims must name the tested
input rather than generalize from one harness. The repeat catches a failure that
the first promising sample misses. Preserve both, not just the preferred sample.
