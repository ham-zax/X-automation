# Reply-quality pilot, 29 October 2026

Status: stopped after two inconclusive writing probes. XR-14 stays in-progress.
No candidate earns production acceptance. No reply in this pilot was published.

## Result

The current static guidance can still produce the unwanted evaluator role.
Replacing the reply instructions does not consistently remove that role.
Removing three systems-focused persona cues also does not remove the recurring
general lesson. Neither candidate justifies a production change from this sample.

Some outputs improve. The result is mixed, rather than a claim that every output
fails. A celebration already works in the baseline. All three versions answer
the direct human-approval question. The repair must preserve those strengths.

The useful outcome is a checked failure of two plausible repairs. More confident
prompt editing would hide that result. The pilot stops before composition and
before using the 18 reserved cases.

## What this experiment runs

This is a static writing simulation. It supplies current Writer persona material,
the Content Operating Standard, and the attached brief's reply guidance. The
sources are historical fixtures, treated as contemporaneous. All variants receive
the same captured full source text. Old replies and analyst assessments stay out
of the writing packets. The solver never receives the other 18 cases.

Live stances, daily tone, relationships in the room, unseen media, linked pages,
thread context, browser state, and feed state are absent. The experiment does not
execute the production Writer, its review, an attached Growth Run, or `act`.
It cannot establish what the complete production system would accept or send.

The task wrapper stays identical across the three writing runs. Each run produces
one sample per source. There is no controlled seed, repeated sample, blind human
rating, or statistical estimate. A changed top-level field can contain several
semantic changes. The result cannot identify one causal sentence.

## Source-by-source assessment

### VA-03: a guide and quickstart

The author shares a Managed Agents guide covering vaults, guardrails, and memory.
The baseline says, "credential handling is the part everyone writes twice."
Candidate B says, "credential vaults are the part everyone postpones until an
agent leaks a key."

Both versions turn a resource share into a universal engineering lesson. The
source does not establish the claims about everyone. Removing the three persona
cues therefore does not remove this observed habit.

Candidate A connects memory with future agent context. That is a more specific
technical contribution. Its ending, "it needs its own permission boundary,"
still prescribes a general requirement. The technical point can be useful.
Its existence does not establish that the reply fits Hamza's intended voice.

### VA-14: the CodeAlta release

The baseline notices the agent-created canvas and congratulates the author.
It already fits the launch. Candidate A gives a shorter celebration. Candidate B
says, "in one release is showing off. respect 🎉" after naming release features.

Candidate B has more playful energy in the parent's assessment. That preference
is not an owner-approved voice label. This case argues against treating all
current output as defective or requiring every reply to change.

### VA-16: AndroidHarness

The complete source explicitly describes on-device shell and git, plus recovery.
No version repeats the historical local-versus-remote question. All versions
can use the full text, yet a product-evaluator comparison persists:

| Version | Exact excerpt |
| --- | --- |
| Baseline | "a demo, not a tool" |
| Candidate A | "just a chat UI with shell access" |
| Candidate B | "the usual 'code from your phone' chat wrapper" |

Candidate A also introduces an interruption "on a call," which the source does
not specify. A plausible scenario is not an observed fact about this app.
Candidate B notices the on-device distinction and avoids assigning an additional
test to the author. That is a useful difference.

A comparison or skeptical opinion is not automatically wrong. The recurring
comparison shows that neither edit cleanly removes the evaluator habit. It does
not prove that every such sentence is condescending. Owner judgment remains
necessary for that boundary. Full source text alone does not settle voice.

### VA-21: an explicit human-approval question

The source asks which action needs human approval. Every version gives an answer.
Candidate B chooses permission escalation and explains its consequence. The
baseline gives two actions despite the source asking for one.

The fresh diagnosis calls Candidate A's "let it branch, test, and open the PR"
an unasked instruction. The parent does not accept that finding as a defect.
The source explicitly invites a policy answer. The sentence can describe the
speaker's allowed workflow. Its imperative form alone cannot establish imposition.

This control matters. A repair that mechanically rejects advice-like grammar,
technical judgment, or all product comparisons would create a different failure.

## What the fresh diagnosis adds

The fresh worker sees the goal, baseline input, exact candidate changes, and all
12 outputs. It receives no parent theory, old published reply, or old assessment.
Its full response remains in `fresh-diagnosis-result.json`.

The worker finds mixed gains and weak causal evidence. It notes that the removed
persona fields are not necessary for portability and permission arguments to
reappear. It also identifies a possible instruction regression: Candidate A
replaces the existing anti-reviewer wording with a broader advice permission.
That is a hypothesis, not an established cause.

The parent rejects three overextensions in the diagnosis:

- Zero questions or relationship callbacks is not a defect in this four-source
  sample. No fixed social mix is required.
- The worker's missing-model-metadata limit applies to its packet. The manifest
  records the actual T3 target and reported option. Decoding details remain absent.
- The packet lacks owner ratings. That does not mean the owner never identifies
  bad replies. The wider investigation starts from that complaint and examples.

The worker proposes 24 additional outputs with blind scoring. No such run occurs.
The proposed count of grounded technical claims could reward extra technical
content, even when a social reply needs none. That metric needs correction before
it becomes an acceptance rule. A quotation match also cannot prove conversational
fit or factual validity of an inference.

## Findings carried forward

1. The current static brief is not proof that the unwanted role disappears.
2. One instructions replacement is not a demonstrated repair.
3. Removing three systems-focused cues is insufficient in these samples.
4. Good launch reactions and direct answers already exist. Preserve them.
5. Source fidelity and voice are separate problems. Full text prevents some
   comprehension errors but does not remove the evaluator stance.
6. Purpose names, word count, lowercase text, and question frequency cannot serve
   as a reply-quality score.
7. One sample per case cannot separate a stable effect from generation variance.
8. The existing review rubric must face concrete drafts before anyone claims that
   a new review gate is necessary. This pilot does not run that rubric.

## Evidence files and reproduction

- `manifest.json` records the frozen split, input hashes, tasks, target, and stop.
- `*-input.json` stores the exact experimental input copies.
- `*-result.json` stores returned text, task identity, and model metadata.
- `writer-task-template.txt` and `diagnosis-task-template.txt` store the wrappers.
- `request-receipts.json` records captured request and summary lengths.
- `comparison.html` presents the four sources and all three writing outputs.

To reconstruct a submitted task, remove the template file's final newline and
replace `{{PACKET_JSON}}` with the input file's complete text. Append the dispatch's
`packetSuffix` from the manifest. Check its SHA-256 against that dispatch.
Preserve the input newline. Only the baseline has an extra newline suffix.
T3 adds its role wrapper. That wrapper is outside these locally hashed task bytes.
Do not rerun the experiment simply to inspect this checkpoint.

The first reconstruction check catches one extra final newline in the submitted
baseline packet. The initial `print()` capture adds it. The staged whitespace
check rejects a physical blank line at the input file's end. The manifest now
records that exact suffix. The task hash preserves the submitted bytes.
The JSON values and all candidate changes remain identical. No model rerun occurs.

Artifact checks cover JSON shape, exact case membership, unchanged sources,
allowed candidate deltas, request hashes, model metadata, output bounds, and secret
absence. These checks establish artifact integrity, not a successful writing repair.

The inline HTML delivery succeeds. Automated visual checking does not run because
the host blocks the preview browser's sandbox through AppArmor. No screenshot or
interaction check is claimed. The host setup command returned by T3 is
`sudo env "PATH=$PATH" t3 browser setup`. No host setting changes in this pilot.

## Short retrospective

The persona-removal hypothesis looked attractive but did not eliminate the habit.
Keep that negative result. Otherwise the next session can repeat a failed edit.

The static packet omits production context and real review execution. Label that
boundary before generating text. A convenient replay must not become a claim
about the full operator.

Large tool metadata and combined reads exceeded output limits during exploration.
Use selected fields and bounded excerpts. Future proposals live in
`docs/FUTURE_IMPROVEMENTS.md`. This retrospective adds no standing agent rules.
