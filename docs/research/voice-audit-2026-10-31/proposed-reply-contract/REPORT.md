# Other AI's reply-contract proposal: offline test

## Scope and method

The user first requests a durable summary of model/context findings, then asks
to test the other AI's proposal. The summary is written first as
`docs/research/REPLY_MODEL_CONTEXT_FINDINGS_2026-10-31.md`.

Six OpenCode DeepSeek V4.1 Flash Free calls request variant max. The candidate
uses the proposed compact Reply contract, persona projection, source packet and
three-field schema: decision, finalText, evidenceUsed. It omits the full Writer
manual, analytical justification fields and recurring systems persona examples.
Three VA-16 repeats and VA-03, VA-14, VA-21 controls run in fixed pairs. Calls run
two at a time under the user's parallel-work preference. No outputs are fed into
subsequent requests. Exact requests, output and execution receipts are retained.

The contract adds one clarification: project identity does not attest arbitrary
personal use or results. Control intents are authored for a guide reaction,
celebration and direct answer. They are not historical generation traces. The
plan records both decisions before generation. This is an adaptation of the
proposal, not a claim that every character of its suggested payload is identical.

This is the generation portion of the proposal. Production review/attribution
alignment, direct-act routing and live reader changes are not implemented.
There is no model judge, production mutation or automatic acceptance threshold.

## Findings

The candidate prevents the specific per-call diff error in these three Android
samples and preserves “can create” in the release sample. Guide interest and the
direct answer are relevant. No clear invented owner biography appears.

The replies still repeatedly choose a feature, explain its significance and add
a takeaway. They are more grounded in places, but do not consistently achieve
the relaxed peer register shown by the Luna full-context examples. This is parent
assessment, not blind owner acceptance or an objective model ranking.

The direct-answer control shows that factual overreach survives this contract.
The prompt's “available”/“every call” and “can create”/“built” examples explicitly
target earlier observed errors on known sources. Avoiding those exact errors is
useful but weak evidence of generalization. These controls have all been exposed
before and are not untouched validation cases. No reliability rate is inferred.

Six responses pass the real structured-output validator. Activity reads contain
no tool actions. Usage and money remain unknown. No model-review or deterministic
content-gate pass is claimed. No public action, browser, real database or production
code changes. Six of six authorized model calls are consumed.

## Decision boundary

Retain the candidate as mixed experimental evidence. Do not promote it as a
complete repair or rewrite production contracts from this set. A model capability
limit is not established. Neither is one causal schema/persona/prompt component.
The proposed source-attribution changes remain a separate untested implementation
decision. The generation experiment does not establish that weakening or widening
any review branch would preserve factual checks.

The owner can now judge whether the more source-grounded but still explanatory
DeepSeek replies are acceptable. No new tuning round, held-out run, stronger-model
dependency or production migration starts automatically from this checkpoint.
